**Traceback — подробное ТЗ для разработки проекта в ML-портфолио**

Редакция от 14 ноября 2026 года.

Этот документ задаёт проектирование, реализацию и проверку системы, которая по описанию бага и необязательному traceback ищет функции, с которых разработчику стоит начать расследование. Числа ниже являются начальными настройками и целями эксперимента. Результаты обучения, скорость и качество предстоит измерить.

**1. Продукт и демонстрация**

Пользователь выбирает снимок Python-репозитория, вводит описание проблемы, при наличии вставляет стек и получает пять функций-кандидатов. Каждую можно открыть на конкретной ревизии, увидеть релевантный участок кода, места в исходной поисковой выдаче и связи с другими кандидатами.

В историческом кейсе доступна кнопка «Раскрыть исправление». После нажатия рядом появляются реальные изменения автора и положение затронутых функций в прогнозе. Система сохраняет исходную выдачу, чтобы пользователь мог проверить результат до просмотра ответа.

Пример для объяснения продукта — сообщение о повторном использовании соединения после тайм-аута. В стеке виден обработчик запроса. Система дополнительно поднимает функцию очистки пула, вызываемую обработчиком. На раскрытом патче можно проверить, менял ли разработчик эту функцию.

Первый релиз поддерживает Python-код и баг-репорты на английском. Интерфейс — на русском. Такое ограничение соответствует стартовым моделям и корпусу. Запросы на русском требуют отдельного эксперимента и своего отчёта.

Результат ранжирования означает полезность кандидата для проверки. Главная доступная историческая метка — участие функции в исправляющем патче. Между этой меткой и истинной причиной дефекта возможны расхождения. Интерфейс, калибровка и отчёт должны сохранять именно эту интерпретацию.

**2. Главная исследовательская гипотеза**

Контрастивное дообучение на правдоподобных функциях из того же репозитория повышает качество локализации по сравнению с готовым энкодером и обучением со случайными отрицательными примерами.

Второй проверяемый вопрос — компенсирует ли cross-encoder дополнительную стоимость вычислений улучшением первых мест. Вклад графа оценивается отдельно при одинаковом числе кандидатов.

Главный результат проекта — воспроизводимое сравнение этих вариантов на зафиксированных данных. Удачная демонстрация дополняет измерения.

**3. Компоненты и владение данными**

| Компонент | Принимает | Возвращает |
|---|---|---|
| Подготовка корпуса | Исторические issue, ревизии, патчи, метаданные | Проверяемые пакеты кейсов, метки, разбиение |
| Индексатор | Снимок исходного кода | Функции, лексический индекс, эмбеддинги, граф |
| Обработчик запроса | Текст пользователя и стек | Представления запроса и привязанные кадры |
| Поиск кандидатов | Запрос и индекс | До 50 уникальных функций с происхождением |
| Cross-encoder | Запрос и фрагменты кандидатов | Оценки функций и порядок кандидатов |
| Калибровка | Признаки завершённого ранжирования | Оценка вероятности попадания первого места в историческую метку |
| Локальный сервис | Запросы интерфейса | Состояния задач, выдача, исходный код |
| Модуль раскрытия | Идентификатор исторического кейса | Патч, исторические метки, сравнение |

Инференс получает разрешённые поля кейса через отдельный контракт. Полный объект датасета остаётся в подготовке корпуса и оценке. Патч и метки хранятся отдельно от поискового индекса. До раскрытия ответа HTTP-ответы интерфейса содержат только данные, необходимые для исследования исходного снимка.

Модель видит исходный код base_commit. Исходная версия, на которой ошибку удалось воспроизвести тестом, получает дополнительную отметку о такой проверке.

**4. Источник данных и первая проверка реализуемости**

Для старта использовать SWE-bench как источник связок issue, исходной ревизии и патча. Для этого проекта строится собственная задача локализации функций и собственный протокол оценки. Поле problem_statement содержит описание, base_commit задаёт снимок, patch нужен для меток. Различия между ревизиями набора требуют фиксации конкретного источника. [Описание набора](https://huggingface.co/datasets/SWE-bench/SWE-bench)

В описании ревизии 9bf0b39a1d4ce5a1338856877724c850fb077720 заявлен train. До планирования большого обучения загрузчик должен проверить фактическую доступность файлов, схему и число строк этого снимка. Если архив недоступен, продолжить со сборщиком собственных issue–PR пар, сохранив общий формат кейса. Доступность обучающих файлов в рамках этого проектирования не проверялась. [Описание зафиксированной ревизии](https://huggingface.co/datasets/SWE-bench/SWE-bench/blob/9bf0b39a1d4ce5a1338856877724c850fb077720/README.md)

Первая инженерная проверка делается на 30–50 кейсах. Нужно восстановить исходные файлы, применить патч для проверки совместимости базы и сопоставить изменения с существовавшими функциями. Эту небольшую выборку удобно использовать для исправления парсера и ручного аудита меток.

Ориентир после аудита — 2–5 тысяч пригодных обучающих кейсов из нескольких репозиториев. Количество определяется доступными данными. Малое число независимых issue ограничивает обобщение даже при большом числе пар «запрос — функция».

При небольшом корпусе основное сравнение следует дополнить кривой обучения. Она покажет, растёт ли результат при добавлении новых issue. Точное количество доступных кейсов и их пригодность нужно опубликовать до интерпретации результата.

**5. Контракт исторического кейса**

| Группа | Поля и смысл |
|---|---|
| Идентичность | case_id, repository_id, source_dataset, source_revision, source_instance_id |
| Источники | issue_url, fix_url, время загрузки, контрольные суммы исходных материалов |
| Версии | base_commit, fix_commit при наличии, хэш дерева исходного снимка |
| Запрос | title, problem_statement_raw, problem_statement_filtered, traceback_raw |
| Время | issue_created_at, issue_text_observed_at, fix_available_at, cutoff_at |
| Происхождение | Способ получения текста, уверенность в исторической версии issue, происхождение стека |
| Метки | Изменённые функции исходного снимка, качество сопоставления, смешанные и неподдерживаемые изменения |
| Аудит | Флаги подсказки решения, группа дубликатов, причины исключения из отдельных срезов |
| Проверка | Статус применения патча, статус воспроизведения тестом, версия процедуры подготовки |

Поле created_at из источника нужно интерпретировать по его фактической семантике. Для временного разбиения важен момент доступности исправления. Если это время восстановлено приблизительно, кейс получает соответствующую отметку.

base_commit из готового корпуса используется как явно заданная база. Для собственного сборщика нужно определить дерево, относительно которого построен патч. Родитель последнего коммита PR может уже содержать часть исправления. Итоговый merge-коммит также требует проверки. Совместимость патча с выбранной базой входит в аудит.

Состояния воспроизведения хранить раздельно. Применение патча к исходным файлам подтверждает совместимость снимка. Запуск падающего теста до исправления и успешного после подтверждает динамическое воспроизведение.

**6. Защита качества данных от утечки ответа**

Текст issue мог быть отредактирован после решения проблемы. В него могли добавить ссылку на исправление, конкретный diff или готовое объяснение. Для SWE-bench публично описаны случаи таких подсказок в problem_statement. Проверка нужна даже при использовании готового набора. [Обсуждение конкретных случаев](https://github.com/SWE-bench/SWE-bench/issues/669)

Для каждого кейса зафиксировать три свойства — историчность текста, наличие явной подсказки и происхождение traceback. Основной строгий срез использует проверенный текст, доступный до исправления, с документированным результатом аудита.

Дополнительно пометить вид задачи — дефект, расширение поведения, рефакторинг или смешанный случай. Issue–PR пара сама по себе не подтверждает, что задача описывает баг. Главный отчёт о поиске дефектов должен указывать состав этого среза.

Для остальных кейсов возможны отдельные срезы. Если историческую версию текста восстановить не удалось, метрики на таком срезе сопровождаются этим ограничением. Автоматическое удаление ссылки из нынешнего issue само по себе историческую версию не восстанавливает.

Разрешённый текст запроса включает исходное описание пользователя, наблюдавшиеся сообщения об ошибке и предоставленные до исправления фрагменты. Комментарии с готовым решением, тесты из исправляющего патча и названия новых FAIL_TO_PASS тестов доступны подготовке меток и проверке.

Технические изменения текста протоколируются. Для каждой версии хранить исходный хэш, хэш результата и причину обработки. Положения удалённых служебных фрагментов помогают проверить, что обработка не уничтожила естественное описание симптома.

Стек из исходного issue и стек, полученный позднее запуском воспроизводящего теста, имеют разное происхождение. Для второго случая отдельно указывается использованный тест. Отчёт должен позволять оценить оба режима.

Открытые репозитории могли присутствовать в предобучении энкодеров. Разбиение проекта и изоляция патчей контролируют доступные этапы этого эксперимента. Пересечение с предобучением остаётся свойством выбранных базовых моделей.

**7. Как получать метки из патча**

Разобрать diff и получить интервалы фактических изменений по старым координатам. Контекстные строки diff нужны для сопоставления. Для каждой изменённой строки найти наиболее вложенную функцию исходного файла, которая ей владеет.

| Ситуация | Правило |
|---|---|
| Изменение или удаление строки внутри функции | Положительная метка для наиболее вложенной функции |
| Изменение сигнатуры или декоратора функции | Метка для соответствующей функции |
| Только добавление внутри существовавшей функции | Сопоставление по границе вставки и структуре исходного узла |
| Вставка между функциями | Статус неоднозначного сопоставления до проверки |
| Новая функция целиком | Метка о добавленной сущности и ограниченной применимости поиска по старым функциям |
| Изменение атрибута класса, импорта или выражения на уровне модуля | Отдельная категория изменений вне функции |
| Переименование файла | Метки и индекс ссылаются на старый путь |
| Правки документации, комментариев или форматирования | Категория вспомогательных изменений |
| Изменения только тестов или конфигурации | Отдельный срез вне основной области локализации |

Для вставок old_count может равняться нулю. Одного пересечения интервалов здесь недостаточно. Нужно проверить положение границы относительно исходных узлов, принадлежность соседних строк и отступы. Неоднозначность сохраняется в метаданных.

Границы вложенной функции относятся к самой вложенной функции. В поисковом представлении внешней функции тело вложенной можно заменить кратким указателем на дочерний символ. В просмотре кода показывается оригинальный файл.

Сохранить долю производственных изменений, для которых удалось получить метку. Отдельно оценивать полностью сопоставленные кейсы и смешанные кейсы, где патч затрагивает функции вместе с модульным кодом.

Функция с положительной меткой участвовала в выбранном исправлении. Неизменённые функции могут быть полезны разработчику и иногда являются альтернативными местами исправления. Это основание для осторожного обращения с отрицательными примерами.

**8. Разбиение данных**

Сначала объединить дубликаты, бэкпорты, связанные issue одного исправления и повторные представления одного патча. Затем построить разбиение групп, сохраняя порядок доступности исправлений.

Для временного протокола задать глобальные границы по fix_available_at. В train входят более ранние исправления, затем идёт валидация, затем тест. Если группа пересекает границы, её можно целиком перенести в более позднюю часть. Метод и число таких переносов фиксируются.

Целый репозиторий выделить для проверки переноса. Выбор репозитория основывать на достаточности и качестве данных до просмотра результатов моделей. Его issue и патчи остаются за пределами обучения и настройки.

Валидацию разделить по задачам. Одна часть выбирает модель и параметры поиска. Другая формирует прогнозы для обучения калибратора. Третья выбирает порог отказа. При малом количестве данных для калибровки допустимы внутренние out-of-fold прогнозы с документированной процедурой.

Функция может естественно существовать и в раннем, и в позднем снимке знакомого проекта. Это соответствует временной задаче. Дополнительно полезен срез новых либо существенно изменившихся символов. Дубликаты одного и того же расследования должны оставаться в одной части.

Демонстрационные кейсы берутся из выделенной разработки или отдельной подборки. Изменения интерфейса на основе этих кейсов не используются как основание для подбора параметров на финальном тесте.

Все сравниваемые варианты используют один набор case_id, одну область кандидатов и одну версию меток. Результаты проекта публикуются как собственная оценка локализации с описанием отбора.

**9. Снимок кода и синтаксический индекс**

Основной парсер — зафиксированная версия tree-sitter-python. Из него извлекаются функции, async-функции, классы, вложенность, декораторы, импорты и места вызовов. У каждого файла сохраняется статус разбора. Ошибки синтаксического дерева и пропущенные интервалы входят в статистику покрытия.

Индекс хранит репозиторий и ревизию явно. Обновление индекса создаёт новый снимок. Запрос закрепляется за одним snapshot_id на всё расследование.

| Сущность | Содержимое |
|---|---|
| Snapshot | SHA дерева, версия парсера, правила области поиска, версия моделей |
| SourceFile | Относительный путь, байты источника, кодировка, хэш, ошибки разбора |
| Symbol | Тип, полное имя, класс и внешний символ, границы, сигнатура, docstring |
| CodeWindow | Фрагмент длинной функции и исходные координаты |
| CallEdge | Вызывающий, вызываемый, направление, место вызова, способ разрешения |
| VectorEntry | symbol_id, вектор, точная версия энкодера и сериализации входа |

symbol_id вычислять из идентичности репозитория, снимка, пути, вида узла, полного имени, начального байтового смещения и хэша исходника. Это различает одноимённые методы и повторные определения.

Поисковое представление и оригинальный исходник хранить отдельно. Для координат зафиксировать единый контракт — номера строк с единицы, конечный байтовый интервал открытый. Преобразование байтовых смещений и видимых колонок проверить на не-ASCII тексте.

Основная область кандидатов — производственные Python-функции, включая приватные методы и функции в __init__.py. Правила исключения тестов, vendored-кода и сгенерированных файлов задаются конфигурацией и входят в отчёт.

Кэш эмбеддингов привязывается к хэшу полностью сериализованного входа, ревизии модели и параметрам токенизации. Путь и сигнатура тоже влияют на этот вход. Это позволяет переиспользовать расчёты без смешения разных представлений функции.

**10. Обработка запроса и traceback**

Обработчик сохраняет оригинальный текст и выделяет заголовок, симптомы, кодовые блоки, исключения, сообщения и кадры стека. Для поиска формируются компактные представления. Правила сокращения одинаковы в обучении и демонстрации.

В лексическом запросе особенно полезны имена классов и методов, редкие части сообщений и идентификаторы из воспроизводящего примера. Удалённые абсолютные пути нормализуются к локальным путям снимка по проверяемому совпадению суффиксов.

Стек разбирается с учётом цепочек исключений. Повторяющиеся кадры можно сворачивать для представления, сохраняя их позиции и исходные строки.

| Привязка кадра | Условия |
|---|---|
| Подтверждённая | Известный снимок, однозначный локальный путь, строка внутри функции, согласованное имя |
| Приблизительная | Путь и имя согласуются, точность номера строки или версии неизвестна |
| Неоднозначная | Существуют несколько подходящих файлов или символов |
| Внешняя | Кадр относится к зависимости за пределами снимка |

У пользовательского traceback версия установленной библиотеки часто отличается от выбранного снимка. Совпадение пути и строки без подтверждения версии отображается как приблизительное.

В поиске учитывать именованные символы из всего стека, а для гарантированных мест списка использовать до десяти наиболее глубоких уникальных локальных функций. При длинной цепочке сохранять информацию о том, какие кадры были отсечены.

**11. Лексический поиск**

Хранилище — SQLite с FTS5. Подготовить отдельные поля для пути, имени, сигнатуры, docstring, сообщений исключений и тела. Индексировать исходные имена и разбиение snake_case и camelCase на части.

Начальные веса полей — имя и сигнатура 4, путь 2, строковые сообщения 2, docstring и тело 1. Это параметры настройки на валидации.

Запрос ограничить информативными термами, сохраняя точные идентификаторы и тексты ошибки. Термы экранировать как литералы FTS и передавать параметрами. Это также делает поведение предсказуемым для строк с кавычками и операторами поиска.

Сохранять позицию функции и исходную оценку. В FTS5 лучший BM25 соответствует меньшему числовому значению. Это учитывается при превращении результата в ранг. [Документация SQLite FTS5](https://www.sqlite.org/fts5.html)

**12. Нейросетевой поиск**

Начальная модель — microsoft/unixcoder-base в encoder-only режиме. Сначала зафиксировать результат готовой модели, затем дообучать её. Для репрезентации использовать официальный способ подготовки режима, маску и pooling, после чего L2-нормализовать векторы. Сходство — скалярное произведение нормированных векторов. Модель выдаёт 768-мерное представление. [Карточка модели](https://huggingface.co/microsoft/unixcoder-base) [Официальная реализация](https://github.com/microsoft/CodeBERT/blob/master/UniXcoder/unixcoder.py)

Bi-encoder в первой конфигурации имеет общий backbone для запросов и кода. Это два независимых прохода через общие веса. Код индексируется заранее. Изменение этих весов создаёт новую версию векторного индекса.

Для каждой функции рассчитывается один вектор обзора. Вход содержит относительный путь, полное имя, сигнатуру, ограниченный docstring и тело. Для длинного тела сохраняются начало и конец с обозначением пропуска. Такая схема удерживает стоимость индексирования и даёт один голос каждой функции при поиске.

Начальная длина запроса — 256 токенов, функции — 512 с учётом всех специальных токенов. В заголовок функции, путь и docstring выделяется до 160 токенов. Остальной бюджет получает тело. Для длинного тела две трети бюджета идут началу и треть концу. Фактические границы задаёт токенизатор.

В длинном запросе приоритет получают заголовок, класс и текст исключения, последние локальные кадры и описание воспроизводимых симптомов. Число и вид обрезанных блоков сохраняются. На длинных функциях и отчётах оценка публикуется отдельно.

Для небольших снимков достаточно точного скалярного поиска по матрице NumPy. Например, 20 тысяч векторов размерности 768 в float32 требуют примерно 61,4 МБ для самой матрицы. При росте корпуса можно добавить индекс приближённого поиска, отдельно измерив потерю полноты.

**13. Граф кода**

Граф строится из символов исходного снимка. В первой версии для расширения используются входящие и исходящие статические вызовы с однозначно определённой целью.

Импорты и алиасы помогают разрешить локальное имя в полный символ. Для self.method учитывается доступное определение класса и область видимости. Динамическая диспетчеризация, присваивания и неоднозначные цели сохраняются как неразрешённые либо приблизительные связи.

У каждого ребра хранить место вызова и способ его получения. На экране пользователь может открыть именно эту строку. Вероятностная интерпретация «90% уверенности ребра» требует отдельной разметки, поэтому стартовая версия использует категории разрешения.

Однозначность статической цели означает однозначность в рамках принятого анализатора. Для методов, которые могут быть переопределены или подменены во время выполнения, сохраняется соответствующая отметка. Фактическое прохождение исполнения через ребро устанавливается отдельной трассировкой.

Начать с одного шага по подтверждённым вызовам. Ранжирование соседей учитывает ранг исходного кандидата и штрафует вершины с большим числом связей. Это ограничивает влияние общих утилит. Вес направления вызова и штраф за степень настраиваются на валидации.

Импорт модуля сам по себе не порождает соседство со всеми его функциями. Такое расширение слишком сильно меняет область поиска. Синтаксическая принадлежность классу остаётся доступной для просмотра и отдельного эксперимента.

**14. Точный алгоритм формирования кандидатов**

Начальные параметры — по 60 функций от BM25 и bi-encoder, итоговый бюджет 50. Более глубокие исходные списки позволяют заполнить бюджет даже при большом пересечении результатов.

Слить лексическую и векторную выдачу через reciprocal rank fusion. Для функции f оценка равна сумме 1 / (60 + rank) по тем спискам, где она встретилась. Веса источников на старте равны. Дедупликация выполняется по symbol_id. Одинаковые оценки разрешаются стабильным порядком идентификаторов.

Алгоритм следующего шага задаётся явно.

1. Добавить до 10 уникальных функций из привязанного локального traceback.
2. Добавить 30 лучших уникальных функций из объединённой выдачи, пропуская уже включённые.
3. По десяти лучшим исходным функциям и кадрам собрать соседей по одному подтверждённому вызову.
4. Добавить до 10 новых соседей по их оценке расширения.
5. Оставшиеся места до 50 заполнить прямыми результатами по RRF, затем оставшимися графовыми соседями.

Когда подходящих функций меньше бюджета, вернуть фактическое количество. Для каждого включения хранить источник, исходные ранги, seed-функцию и ребро расширения при наличии.

При отключённом графе его места заполняются прямыми кандидатами. Для сравнения полная система и вариант без графа должны иметь одинаковый конечный бюджет в тех снимках, где такое количество функций доступно.

Сохранять кандидатов до и после расширения. Это позволяет измерить, какие положительные функции граф добавил и какие были потеряны из-за изменения состава списка.

**15. Обучение bi-encoder**

Пусть P(q) — множество известных положительных функций исходного снимка. Множество D(q) содержит положительные и выбранные отрицательные функции. Оценка s(q,f) равна cosine(q,f) / temperature. Начальная temperature — 0,05.

Обучение минимизирует среднюю по всем положительным функциям отрицательную логарифмическую вероятность в softmax по D(q). У каждого известного положительного примера есть целевая масса. Это соответствует интересу к нахождению нескольких мест исправления.

Внутри батча для каждого запроса строится собственная маска допустимых кандидатов. Известные положительные функции того же исправления сохраняют положительную метку. Дубликаты и неоднозначные копии проверяются до включения в отрицательные.

Начальная конфигурация использует 8 запросов в микробатче и накопление градиентов до эффективных 32 запросов. Для in-batch negatives реальный пул определяется микробатчем. Накопление градиентов само по себе его не расширяет.

Первый этап обучается на случайных функциях из того же исходного снимка вместе с допустимыми in-batch примерами. Затем зафиксированный checkpoint добывает трудные кандидаты только для обучающих запросов.

На один запрос второй этап начинает с 12 явных отрицательных примеров — четыре случайных из снимка, четыре из BM25 и четыре из выдачи энкодера. При пересечении списков брать следующие уникальные функции.

Кандидаты того же модуля, одноимённые методы других классов и связанные функции особенно полезны для проверки трудных случаев. Они также чаще несут шумную метку. Ручной аудит небольшой выборки нужен до выбора их пропорции.

Первое сравнение использует одинаковые правила маскирования. Затем можно проверить пониженный вес сомнительных негативов как отдельный вариант. Конкретная корректировка функции потерь должна сохраняться в конфигурации опыта.

Для честного сравнения контрольная модель со случайными негативами получает столько же шагов обучения, сколько модель с дополнительным этапом hard-negative mining. Иначе рост качества можно ошибочно приписать только способу выбора примеров.

Начальные параметры обучения — AdamW, learning rate 2e-5 для backbone, weight decay 0,01, warmup 10%, ограничение нормы градиента 1. Число эпох выбирать по валидации с верхним пределом 5 на этап. При нехватке памяти уменьшать микробатч и фиксировать новое число in-batch примеров.

Checkpoint выбирать по Hit@50, а Recall@50 использовать как дополнительный критерий при близких результатах. Главная диагностика первого этапа — присутствует ли хотя бы одна полезная историческая цель среди кандидатов.

Синтетические перефразирования можно добавлять после измерения на настоящих issue. Производные одного исходного issue остаются в одной части данных. Приведённый пользователем стек и описанные идентификаторы сохраняют естественную роль наблюдений.

**16. Cross-encoder и длинные функции**

Начальная основа — microsoft/codebert-base с обучаемой головой из одного скалярного выхода. Он совместно читает запрос и код кандидата. Этот checkpoint требует обучения под ранжирование. В его исходной карточке описаны предобучение на документации и коде и задачи, для которых опубликованы примеры использования. [Карточка CodeBERT](https://huggingface.co/microsoft/codebert-base)

Для пары используется стандартное парное оформление токенизатора. Общий предел — 512 токенов. Начальный бюджет — до 128 на запрос, до 48 на путь, класс и сигнатуру и до 332 на тело. Оставшиеся четыре места резервируются под специальные токены. Реальный сериализатор проверяет общий предел.

Полное тело длинной функции делится на окна с перекрытием 96 токенов. Каждое окно получает одинаковую краткую информацию о владельце. Для запроса отбираются максимум три окна по наблюдаемым признакам.

Приоритет имеют окно с точно привязанной строкой traceback, окно с редкими словами и идентификаторами запроса и начало функции. Повторы удаляются. Если совпадений мало, свободное место занимает фрагмент другой части функции. Координаты исправления в выборе окон участвуют только при последующей оценке.

Обучение использует тот же селектор окон, что и поиск. Иначе модель получит при обучении фрагменты, которых может не получить в настоящем запросе.

Оценку функции агрегировать через нормированный log-sum-exp по оценкам отобранных окон. Начальная температура агрегации — 1. Для сравнения сохранить max-pooling. Нормировка по числу окон уменьшает прямое преимущество от их количества, но влияние длины всё равно нужно проверить по срезам.

Лучшее окно по собственной оценке показывается первым. Подсветка означает, что ранжировщик счёл этот фрагмент релевантным. Правильность локализации конкретной строки требует отдельной разметки.

Cross-encoder учится на списках из 16 функций с положительными и отрицательными примерами. Использовать до четырёх положительных функций и заполнение списка кандидатами поисковой системы. Если положительного кандидата в обучающей выдаче нет, его можно добавить с сохранением такой отметки для анализа.

Вход модели содержит только запрос и код. Служебная отметка о добавленном положительном примере остаётся в журнале обучения. Состав списка перемешивается перед обучением.

Функция потерь — listwise cross-entropy с целевой массой, распределённой между положительными функциями. Один запрос получает сопоставимый вес независимо от числа затронутых функций.

В валидации и тесте используются фактические кандидаты поиска. Отчёт показывает условное качество ранжирования, когда цель попала в список, и общее качество системы. Это позволяет увидеть предел, заданный поиском.

**17. Окончательный порядок и калибровка**

В основной конфигурации окончательный порядок задаёт оценка cross-encoder. При равенстве используются RRF и стабильный идентификатор. Источники попадания и признаки графа остаются доступны для анализа и калибровки.

Калибратор оценивает строго определённое событие — первая функция выдачи принадлежит множеству исторических функций, изменённых исправлением. Формулировка в карточке модели должна соответствовать этому событию.

Начальная модель калибровки — регуляризованная логистическая регрессия на небольшом наборе признаков. Включить оценку первого места, разницу между первым и вторым, исходные ранги, согласие поисковых источников, наличие и качество привязки стека, длину кандидата и факт сокращения запроса.

Отдельно проверить, что калибратор не опирается на идентификатор репозитория и не обучается на окончательном тесте. Масштабирование числовых признаков обучается вместе с калибратором на выделенных прогнозах.

Для порога использовать другую валидационную часть либо out-of-fold процедуру. Ориентир эксперимента — точность первого места среди принятых запросов не ниже 80% при покрытии не ниже 30%. Это целевой режим, достижимость которого ещё нужно проверить.

На тесте опубликовать coverage, selective accuracy, Brier score и диаграмму надёжности с количеством наблюдений в каждом интервале. При небольшом числе наблюдений особенно важны доверительные интервалы.

При низкой оценке интерфейс показывает список кандидатов со статусом «Недостаточно данных для уверенного первого выбора». Детерминированная подсказка может попросить стек, если его нет, или версию библиотеки, если привязка приблизительная.

На новом репозитории распределение может измениться. Качество калибровки и отказа на удержанном репозитории оценивается отдельно.

**18. Метрики с точными определениями**

Пусть P — множество размеченных функций кейса, R_K — первые K уникальных функций. Метрики считаются по функциям, после объединения окон.

| Метрика | Определение | Что показывает |
|---|---|---|
| Hit@K | 1, если пересечение P и R_K непустое, иначе 0. Затем среднее по кейсам | Дошёл ли разработчик хотя бы до одного исторического места исправления |
| Recall@K | Размер пересечения P и R_K, делённый на размер P. Затем среднее по кейсам | Какая доля размеченных функций найдена |
| MRR | Обратный ранг первого совпадения, с нулём при его отсутствии в заданной глубине | Насколько рано встречается первое совпадение |
| Coverage | Доля запросов с принятым первым выбором | Как часто система предлагает уверенный первый шаг |
| Selective accuracy | Hit@1 среди принятых запросов | Как часто принятый первый выбор совпадает с меткой |
| Graph gain | Разница Hit@K и Recall@K при включении графа на одних кейсах | Компенсирует ли расширение изменение состава списка |
| Latency p50/p95 | Квантили времени по зафиксированному списку запросов | Стоимость режима на указанном оборудовании |

Важное отличие от короткой исходной схемы — попадание хотя бы в одну функцию и полнота по всем функциям имеют разные названия и смысл. Для поиска кандидатов публикуются обе метрики.

У MRR указать глубину списка. MRR@50, полученный после полного ранжирования кандидатов, и MRR@5, ограниченный пользовательскими карточками, описывают разные условия.

Итоговые таблицы включают количество кейсов, функции на снимок, число положительных меток, покрытие области задачи и распределение по репозиториям. Помимо среднего по issue полезно среднее по репозиториям, чтобы один большой проект не определял весь результат.

Для сравнения систем использовать парный bootstrap по группам независимых исправлений с фиксированным seed и доверительными интервалами. При малом числе удержанных репозиториев вывод о переносе формулируется в пределах проверенных проектов.

**19. Матрица обязательных экспериментов**

| Вариант | Назначение сравнения |
|---|---|
| Последний локальный кадр | База для кейсов, в которых стек предоставлен |
| BM25 | Качество лексики и идентификаторов |
| Готовый UniXcoder | Отправная точка нейросетевого поиска |
| Дообученный энкодер со случайными негативами | Вклад самого дообучения |
| Энкодер с hard negatives при том же бюджете обучения | Главная гипотеза проекта |
| BM25 + лучший энкодер | Вклад объединения источников |
| Гибридный поиск с графом и без него | Вклад графовых соседей при равном бюджете |
| Одинаковые кандидаты до и после cross-encoder | Вклад совместного чтения запроса и кода |
| Полная система с порогом и без него | Цена отказа и качество принятых результатов |

Отдельные срезы — стек присутствует, стек отсутствует, размеченных функций нет в локальном стеке, длинные функции, несколько положительных меток, новые символы, удержанный репозиторий и проверенный исторический текст.

Заранее подготовить сетку бюджета кандидатов 20, 50 и 100. На валидации выбрать компромисс полноты и задержки. После выбора зафиксировать режим перед итоговой оценкой.

Проигранные сравнения остаются в отчёте. Если граф или cross-encoder не дают измеримого выигрыша, основной рабочий профиль может использовать более короткий путь. Экспериментальные варианты сохраняют воспроизводимую конфигурацию.

**20. Интерфейс и проверяемые свидетельства**

Главный экран делится на список кандидатов, просмотр кода и панель наблюдений. Сверху видны репозиторий, короткий SHA снимка и текущий режим.

Карточка кандидата показывает путь, полное имя, строки, место в выдаче и свидетельства попадания. Пользователь может открыть локальный кадр стека, совпадение редкого терма или ребро вызова, по которому функция попала из соседнего модуля.

Числовые оценки методов доступны в панели сравнения с понятными подписями. Калиброванная вероятность подписывается как вероятность совпадения первого места с исторической меткой. Пользовательский текст и исходный код отображаются с корректным экранированием.

Режим сравнения фиксирует один запрос и один снимок. Переключатель метода меняет результаты, сохраняя исходный текст. Панель показывает, какие кандидаты добавились, исчезли или поменялись местами.

Для сохранённого исторического расследования кнопка раскрытия загружает патч отдельным действием. Она показывает все затронутые функции, включая те, которые модель пропустила, и сопоставляет их с зафиксированной выдачей.

Предусмотреть три демонстрации — прямое попадание стека, исправление вне стека и недостаточный исходный контекст. Последний сценарий нужно выбрать по фактическому поведению модели на демонстрационной части. Сохранённые прогоны можно показывать с явной подписью о сохранённом результате.

У произвольного пользовательского репозитория историческое исправление появляется только при наличии соответствующего кейса. Обычный поиск остаётся полноценным сценарием.

Генеративный комментарий — отдельное расширение после проверки поиска. Для него вход состоит из найденных фрагментов и наблюдений с идентификаторами. Каждое утверждение о конкретном коде должно ссылаться на существующую строку или символ, а вывод о возможной причине сохраняет статус гипотезы.

**21. Локальный стек и контракты сервиса**

Python 3.11 или 3.12, PyTorch и Transformers для моделей, tree-sitter-python для кода, SQLite FTS5 и NumPy для индекса, FastAPI для сервиса, React с TypeScript для интерфейса. Зависимости фиксируются lock-файлом. Бренд проекта — Traceback, имя Python-пакета — traceback_lab, чтобы сохранить корректный импорт стандартного модуля traceback.

Обучение запускается отдельным процессом. Для демонстрации сервис загружает готовые веса и индекс. Backend и собранный frontend обслуживаются одним локальным приложением.

| Операция | Контракт |
|---|---|
| Получить снимки | GET /v1/snapshots возвращает идентичность, ревизию, покрытие и совместимую модель |
| Создать расследование | POST /v1/investigations принимает snapshot_id, текст, traceback и профиль. Возвращает идентификатор задачи |
| Узнать состояние | GET /v1/investigations/{id} возвращает этап, результат или диагностируемую ошибку |
| Открыть символ | GET /v1/snapshots/{snapshot_id}/symbols/{symbol_id} возвращает исходный код и координаты |
| Раскрыть кейс | POST /v1/cases/{case_id}/reveal возвращает отдельные исторические материалы |
| Получить сведения о модели | GET /v1/models возвращает версии весов, индексирования и калибровки |

Локальный репозиторий индексируется командой с явными путём и ревизией. Интерфейс выбирает уже зарегистрированный снимок. Индексирование читает исходники как данные.

Состояния задачи — queued, parsing, retrieving, reranking, completed, failed и cancelled. Тяжёлые вычисления выполняются в ограниченном пуле, сохраняя отзывчивость HTTP. Для локального приложения достаточно очереди в процессе с ограничением параллельных инференсов.

Индекс собирается во временный каталог, проверяется и публикуется атомарно. Одновременные запросы продолжают использовать закреплённые снимки. При повторном запуске индексирования задача использует ключ из снимка, конфигурации и модели.

Ключ кэша расследования включает снимок, нормализованный запрос, стек, профиль, версии весов и калибратора. Кэширование результата и прогрев модели учитываются при замере задержки.

**22. Производительность и поставка**

Целевая среда демонстрации — CPU и 16 ГБ RAM. Это планируемый бюджет, который предстоит проверить. Для полного дообучения ориентироваться на доступный GPU с подбором микробатча по памяти. Фактические аппаратные условия входят в отчёт.

Полный профиль начинается с 50 функций и максимум трёх окон на функцию. Это до 150 пар для cross-encoder. Его стоимость на CPU может оказаться значительной, поэтому отдельно измерить количество токенов и время каждого этапа.

Быстрый профиль может использовать 20 кандидатов и одно выбранное окно. Его качество и задержка публикуются отдельной строкой. При переключении профиля пользователь видит выбранный режим.

Первый экран, выбор кейса и открытие исходного кода должны работать сразу после запуска приложения. Во время инференса показывать текущий этап. Числовую цель задержки выбрать после первого профилирования на конкретном CPU и зафиксировать до итогового сравнения моделей.

Оптимизация весов через ONNX или int8 проверяется отдельным сравнением. Сохранить эталонные входы, сопоставить оценки и конечные ранги, измерить качество на валидации. Калибратор относится к той версии вычислений, на которой он проверен.

GitHub хранит исходники, конфигурации, манифесты кейсов и небольшие отчёты. Готовые веса и индексы поставляются версионированным релизом с контрольными суммами. Полный демонстрационный комплект включает нужные модели, токенизаторы и подготовленные кейсы.

Для получения моделей допустима разовая подготовка окружения. Дальнейший запуск из полного комплекта должен проходить автономно. Инструкция явно описывает состав скачивания и объём.

| Проверка | Какой дефект обнаруживает |

Маленькие синтетические репозитории полезны для проверки механики парсера, графа и метрик. Качество обученной модели измеряется на исторических кейсах.

CI выполняет проверки контрактов и небольшое сквозное расследование с компактными артефактами. Полный корпус и обучение запускаются отдельными воспроизводимыми заданиями.

**24. Этапы разработки и артефакты приёмки**

| Этап | Конкретный результат | Условие перехода |
|---|---|---|
| Аудит | 30–50 восстановленных кейсов и статистика причин исключения | Подтверждены доступность данных и смысл меток |
| Вертикальная версия | Снимок, парсер, BM25, просмотр кода, раскрытие патча | Один кейс проходит через все слои |
| Базовые измерения | Фиксированное разбиение и результаты BM25 и готового энкодера | Можно повторить оценку из сохранённого манифеста |
| Обучение | Checkpoint со случайными негативами и равнобюджетный вариант с трудными | Есть измеренный ответ на главную гипотезу |
| Уточнение поиска | Граф, cross-encoder и сравнение состава кандидатов | Для каждого добавления известны вклад и стоимость |
| Калибровка | Отдельные прогнозы для настройки и тест отказа | Вероятности привязаны к определённому событию |
| Релиз | Готовые веса, индексы, три демонстрации, инструкция запуска | Другой человек проходит сценарий из чистого окружения |

Финальный репозиторий содержит код подготовки данных, обучение и оценку, локальное приложение, конфигурации экспериментов, модельную и датасетную карточки, инструкции получения артефактов и таблицу результатов.

У каждого опубликованного результата есть dataset revision, case manifest, commit проекта, модель, seed, параметры поиска, версия парсера и сведения об оборудовании. Пустые измерения остаются обозначенными как ожидающие выполнения.

Приёмочный сценарий состоит из выбора незнакомого кейса, получения пяти функций, открытия свидетельств, раскрытия патча и проверки результата. Затем выполняется оценка на зафиксированном списке кейсов и воспроизводится сравнение с базовыми методами.

Разработчик сначала реализует вертикальный путь с настоящим историческим кейсом, затем наращивает модели по этапам. Решения об изменении начальных параметров сопровождаются измерением или конкретной обнаруженной несовместимостью.

**25. Пояснение для передачи модели-разработчику**

Реализуй Traceback по этому документу. Считай стартовыми решениями Python как язык анализируемого кода, англоязычные issue, UniXcoder для retrieval, отдельный CodeBERT для reranking и локальный интерфейс на русском. Сохраняй объяснимое происхождение каждого кандидата и отдельное хранение исторических ответов.

Первым результатом сделай работающий путь от выбранного исходного снимка и одного issue до выдачи BM25, просмотра функций и раскрытия реального патча. Проверь получение меток на чистых вставках и вложенных функциях. После этого подготовь зафиксированный корпус и сравни базовые методы.

Главное обучение — bi-encoder со случайными и трудными негативами при одинаковом числе шагов. Cross-encoder, граф и калибровку добавляй с отдельными измерениями. Все числа качества публикуй вместе с условиями эксперимента и реальным числом независимых кейсов.

Готовый результат должен позволять человеку запустить историческое расследование из подготовленного релиза, проверить найденные функции по оригинальному исправлению и повторить таблицу оценки. Данный документ описывает архитектуру. Фактическая доступность выбранного обучающего архива, качество моделей и аппаратные требования требуют проверки при реализации.
